# v0.2 로 가는 길 — 확인된 것과 남은 것

## 1. 폰트가 RAM을 거치는가 → **아니다** (확인 완료)

명령 트레이서로 글리프 읽기 3,072회를 전부 잡았다. **100% 카트 ROM 직접 읽기**다
(`0x24C4D8~0x24CE1F`). RAM 사본이 없다.

```
24B288  LD HL,WA / AND HL,0x1FF / SLL 3,HL
24B293  ADD XHL,0x24E38A     ← 카트 주소를 직접 만든다
24B2D0  LD A,(XHL+)
```

SS2 식 「문자열 초기화에 훅을 걸어 RAM에 글리프 페이지를 붓는다」를 그대로 쓰려면
**RAM 버퍼를 새로 만들어야** 한다. 그런데 빈 RAM이 없다 —
RAM 덤프 136개를 교집합해 보니 **항상 0인 가장 긴 구간이 512바이트**다
(`0x63DC~0x65DB`). 글리프 페이지 2KB가 안 들어간다.

→ RAM 뱅킹은 이 롬에선 값이 비싸다. **표를 옮겨 늘리는 SS1 방식이 맞다.**

## 2. SS1 방식이 옳다 — 다만 **목적지 증명**이 관건이다

SS1 은 대사 폰트 표를 `0x08FD2B` → `0x1CBE45` 로 옮겨 153→248칸으로 늘렸다
(`ss1_fontpatch2.py`). KOF R-2 도 베이스가 `0x04B295` 의 imm32 하나라
**옮기는 것 자체는 4바이트 패치**다. 실제로 해 봤고 화면도 정상이었다.

**문제는 목적지였다.** 2bpp 폰트 자리(`0x04C400`)를 골랐는데, 6,000프레임 읽기 지도에서
0회였고 예전 조사에서도 「덮어도 안 바뀐다」고 나왔지만 — 전수 검사하니:

```
0x24AE8A  LD XIY,0x24C40A      0x24B24A  ADD XHL,0x24C40A
0x24B369  ADD XHL,0x24C40A     0x24BFD1  LD XHL,0x24C40A
0x24C0DE  LD XIY,0x24C40A
0x0559D8  그 구역을 가리키는 자원 포인터 표
```

**코드 5곳이 쓰고 있었다.** 안 읽힌 건 그 화면들을 안 가 봤기 때문이다. → 되돌렸다.

## 3. 자유 구역을 판정하는 법 (도구 완비)

| 도구 | 하는 일 |
|---|---|
| `kof_freecheck.py <롬> <시작> <끝>` | 그 구역을 **가리키는 포인터가 있는지** 전수 검사 |
| `kof_freefind.py <롬> <필요바이트>` | 포인터가 하나도 없는 연속 구역을 **후보로** 나열 |

`kof_freefind.py rom/orig.ngc 2600` 으로 후보 **120곳**이 나온다. 큰 것부터:

```
0x0E8007~0x0EC09F  16,536B   0x0CC0DC~0x0CFBC8  15,084B
0x148373~0x14BA18  13,989B   0x0B4015~0x0B7400  13,291B
```

**그러나 포인터가 없다는 것은 비었다는 증명이 아니다.** 폰트 표 자신도
가리키는 것이 코드 즉치값 하나뿐이었다. 계산으로 주소를 만드는 데이터는 안 잡힌다.

### 목적지 검증 절차 (반드시 이 순서로)

1. `kof_freecheck.py` 로 포인터 0 확인
2. 그 구역을 **눈에 띄는 무늬로 덮은 롬**을 만든다
3. `dump/SCREENS.md` 의 화면 목록을 **전부** 돌며 캡처
4. 원본 캡처와 **픽셀 대조**해 한 곳도 안 바뀌었음을 확인
5. 그래도 실기에서 한 번 더 본다

3~4 를 건너뛰면 이번과 같은 사고가 난다.

### 3-A. 도구를 고쳤다 — `kof_freefind.py` 가 24비트를 안 봤다

1순위 추천이던 `0x0F3239~0x0FC000` 을 `kof_freecheck.py` 로 검사하니
`0x2F8130`·`0x2F9130` 을 가리키는 **24비트 포인터가 여럿** 있었다.
freefind 는 32비트만 세고 있었고, TLCS-900H 는 `LD XHL,imm24` 를 흔히 쓴다.

24비트를 구역 자르기에 그대로 쓰면(우연 일치 13만 건) 후보가 **0곳**이 되어 못 쓴다.
그래서 **자르는 기준은 32비트로 두되, 24비트 「지목 수」를 후보마다 찍어 그 순으로 정렬**
하도록 고쳤다. 지목이 적은 것을 고르면 된다.

### 3-B. 검증 결과 — 후보 둘이 1차 통과

`tools/b_tour2.txt` 로 순회를 6화면 → **18화면**으로 넓혔다
(타이틀·메인·전적·게임선택·모드선택·캐릭터선택 3단계·픽 후·전투 진입·전투 2컷).

| 후보 | 크기 | 24비트 지목 | 18화면 픽셀 대조 |
|---|---|---|---|
| `0x0E5559~0x0E6165` | 3,084B (385칸) | 11 | **차이 0** |
| **`0x0BA8A9~0x0BBB00`** | **4,695B (586칸)** | 17 | **차이 0** |

**`0x0BA8A9` 면 512칸 폰트표(4,096B)가 통째로 들어가고 599B 남는다.**

**아직 확정이 아니다.** 18화면도 전부가 아니다 — 스파링 설정 · 기술 장착 · 기술 교환 ·
스테이지 선택/설명 · 엔딩 · 통신(DC) 은 아직 안 갔다. 거기까지 돌고,
그 다음 실기에서 한 번 더 본 뒤에 옮긴다.

## 4. 예산 계산은 자동화돼 있다

`kof_budget.py <롬> <구간> <번역>` 이 **남은 일문이 실제로 쓰는 가나**를 세어
지금 쓸 수 있는 칸을 알려 준다. 177 은 상수가 아니다.

현재: 미번역 일문 1,935줄이 가나 80칸 중 **74칸**을 쓴다 → 안전 예산 **112칸**.
표별로는 대사 71칸 · 스킬 70칸 · 스토리 68칸을 쓴다.
**큰 대사 표를 통째로 끝내야 예산이 열린다** — 조금씩 번역해선 안 는다.

## 5. v0.2 순서 제안

1. **자유 구역 하나를 §3 절차로 검증**한다. 성공하면 표를 옮겨 250칸 이상 확보
2. 확보되면 스킬·아이템 590줄과 스테이지를 넣는다 (번역 초안은 `dump/tr_later/` 에 있다)
3. 안 되면 어휘 재설계로 간다 — 「번역 후 깎기」가 아니라 **「쓸 수 있는 글자로 짓기」**:
   초안 → 음절 빈도 → 1~2회 음절만 재작문 → 반복
4. 어느 쪽이든 **화면 단위로** 끊어 완료한다. 한 화면에 한글·일문이 섞이면 안 된다
