## 2. 그림 타일맵 (②) — 전부 해결

### 구조

    [타일 데이터 n×16B][맵]
    맵 = [행수 1B] { 셀바이트 … 0xFF } × 행수
    셀바이트 = 타일번호×2 + (1이면 좌우반전)
    타일블록 = 맵주소 − n×16

타일은 2bpp, 워드 리틀엔디언, 픽셀 k = `(w >> (14-2k)) & 3`.

### ⚠ 되읽기 검증할 때의 함정

패치 뒤 `spec()` 을 다시 부르면 **타일 주소가 어긋납니다.**
`tile = map − n*16` 으로 역산하는데, 압축으로 n 이 줄면 게임이 읽는 주소와 달라집니다.
**되읽을 때는 반드시 원본 롬 기준 `tile` 주소를 쓰세요.** 저도 여기서 한 번 헛봤습니다.

### ⚠ 압축은 적입니다

`inject` 는 예산 초과 시 닮은 타일을 강제 병합합니다. **걸리면 획이 무너집니다.**

    아마쿠사 → 마마쿠사   (ㅇ 이 ㅁ 으로)
    카즈키   → 가즈키     (ㅋ 윗획 소실)

그래서 압축에 맡기지 말고 **한도에 들어갈 때까지 글자를 줄이는** 방식으로 바꿨습니다
(`gfx3.fit()`, `fan.render(..., d)`). 의외로 **x 위치를 1~4px 미는 게 큽니다** —
글자가 8px 타일 경계에 맞물리면 고유 타일이 확 줄어듭니다.
「아마쿠사」는 Galmuri11 을 2px 왼쪽으로 밀어 정확히 12/12 로 들어갔습니다.

## 3. 타이틀 로고 — 영문판이 두 벌입니다

이 롬은 JUE 판이라 본체 언어 설정에 따라 **다른 그래픽 세트**를 씁니다.
기존 패치는 일본어 세트만 갈아서 영문 설정에서는 원문이 나왔습니다.

| | 본로고 | 부제 팻말 |
|---|---|---|
| 일본어 | `L.A` 20×6 (160×48, 타일 87) | `L.B` 17×5 (136×40, 타일 66) |
| 영문 1벌 | `0x08EA59` 20×6 (타일 105) | `0x08F019` 19×5 (152×40, 타일 84) |
| 영문 2벌 | `0x08DCB4` 19×6 (152×48, 타일 95) | `0x08E20E` 17×5 (타일 78) |

**한 벌만 갈면 나머지에서 영문 로고가 튀어나옵니다.**

### 캔버스 → 블록 대응 (실측으로 확정)

원본 2벌 블록이 1벌 블록의 어디를 잘라낸 것인지 롬 데이터끼리 전수 대조했습니다.
**본로고·부제 모두 dx=8** 입니다. 1벌 본로고는 화면 x=0 이므로 **캔버스 x = 화면 x** 가 성립합니다.

    1벌 본로고(160px) → 캔버스 x   0~159
    1벌 부제  (152px) → 캔버스 x   8~159
    2벌 본로고(152px) → 캔버스 x   8~159
    2벌 부제  (136px) → 캔버스 x  16~151

전에 2벌 본로고를 「좌우 4px 씩 잘라 가운데 맞춤」으로 임의 처리해서 4px 어긋났었습니다.
가운데 정렬은 근거가 없었습니다. 지금은 `2벌 = 1벌의 8px 지점` 이 **0px 오차**로 성립합니다.

## 4. 대사 (①)

    표 포인터   파일 0x069968  →  원본 표 0x08FD2B  (CPU 0x28FD2B)
    확장 표     파일 0x1CBE45  (패치 후)
    렌더러      CPU 0x20F82B   →  파일 0x00F82B
    재배치 영역 0x36900 ~ 0x4FF00 (0xFF 자유 영역)

### 제어 코드 — 이것뿐입니다

원본 대사 198문장 전체를 훑어 확인했습니다.

    F8       줄바꿈
    FA F9    페이지 넘김 + 지우기
    FF       끝
    (0x91·0x92·0x93 은 글리프. 0x92 = 공백)

**「즉시 표시」 같은 코드는 없습니다.**

### 원본은 8×8 가나 2줄, 한글판은 상/하 반쪽

원본 페이지의 F8 구간 길이가 11/16, 15/12, 16/9 처럼 **제각각**입니다 → 진짜 두 줄입니다.
한글화는 이걸 윗줄=초성+중성, 아랫줄=받침으로 전용했습니다.
그래서 엔진이 **윗줄을 끝까지 찍고 나서 받침줄을 찍습니다.** 이게 L 항목의 원인입니다.

### 한 줄 17칸은 정상입니다

17칸짜리 시험 문장을 넣고 실기로 확인했습니다. 줄 넘침 문제는 **없습니다**.

### 미번역 14문장은 이미 들어가 있습니다

잔여텍스트 문서가 지목한 초필살기·승리 대사 14문장은 번역표에 이미 있습니다.
184가 아니라 **198문장**이 빌드됩니다. 문서 쪽이 오래됐습니다.

빌드 로그의 `보류 8개` 는 실패가 아닙니다. 포인터 후보 중 뒷바이트가 뱅크값(0x00/0x34)이
아닌 걸 걸러낸 오탐이고, 문장마다 실제 포인터는 `assert n > 0` 로 보장됩니다.

## 5. ASCII 폰트 (③) — 압축입니다. 확정.

제가 이 건으로 두 번 말을 바꿨습니다. 최종 결론은 **v0.5 README 가 맞다** 입니다.

`0x05291D` 뱅크는 평문이지만 **화면에 쓰이지 않는 별도 사본**입니다.

### 근거 넷

1. **화면 글리프와 뱅크가 픽셀 단위로 같다** — 메뉴를 원본 해상도로 복원해 대조하니
   `1 P D E S U` 전부 완전 일치. 그래서 처음에 「이 뱅크가 쓰인다」고 오판했습니다.
   같은 건 *폰트 디자인*이지 *데이터 출처*가 아닙니다.
2. **뱅크를 고쳐도 화면이 안 바뀐다** — `0x21`·`0x22`·`0x23` 에 한글을 써넣고 문자열을
   그 코드열로 바꿨더니, **문자열 치환은 먹혔는데(글자 수·위치가 바뀜) 글리프는 문장부호 그대로**.
   `0x015A00` 의 `0` 을 통짜로 막아도 타이머는 멀쩡히 `60` 표시.
3. **코드 0x60 이상이 소문자로 나온다** — 우리 뱅크는 그 자리가 전부 `FF`(빈칸)인데
   화면엔 `g h i` 가 나옵니다. 실제 폰트가 소문자까지 갖춘 더 큰 폰트라는 뜻입니다.
4. **그 소문자가 롬 어디에도 평문으로 없다** — 화면에서 뜬 `g`·`h` 비트맵으로 롬 2MB 전수 탐색.
   1bpp MSB/LSB, 2bpp 리틀/빅엔디언, 잉크값 두 가지 — **전부 0건**.
   에뮬레이터 바이너리도 0건이라 BIOS 폰트도 아닙니다.

→ 카트리지 안에 있는데 평문이 아니다 = **압축**.

### 좋은 소식

- 폰트는 **카트리지 안**에 있습니다. 패치 가능한 대상입니다.
- **글리프 디자인은 이미 손에 있습니다** — `0x05291D` 사본이 화면 폰트의 `0x20~0x5F` 와
  픽셀 단위로 같습니다. 압축만 풀면 넣을 그림은 준비돼 있는 셈입니다.
- **문자열 치환 자체는 동작이 확인**됐습니다. 코드를 바꾸면 글자 수와 위치가 그대로 따라옵니다.

## 6. 받침 타이핑 (L) — 렌더러가 타일을 한 장만 읽습니다

### 레코드 형식

    [타일수 1B][타일 16B씩][행수 1B][행마다 타일인덱스…0xFF]
    행 맵 바이트 = 타일번호×2 + 좌우반전
    코드 0x95 = 6타일 4행 (말풍선 프레임, 182B)
    코드 0x96·0x97 = 2타일 2행 (38B)

형식만 보면 **한 음절을 코드 하나로 8×16 통짜 출력**이 가능해 보입니다.

### 실측 3단계

**1단계** 원본 `0x96` 과 바이트 구조가 동일한 2타일 2행 레코드로 한글 음절 16종을 만들어
6번 문장을 `F8` 없이 음절 코드만 나열 → **윗줄 6칸 픽셀 단위 일치, 아랫줄만 엉뚱**.

**2단계** 단일 문자 탐침(위=꽉찬 블록, 아래=테두리) → **행 2 를 같은 칸 바로 아래에 그리는 것 자체는 정상**.
커서도 1칸씩 정상 전진.

**3단계** 타일 3장 넣고 행2 맵 바이트 `0x00`~`0x05` 전수 시험:

| 맵 바이트 | 기대 | 실제 |
|---|---|---|
| `0x00` `0x01` | 타일0 / 타일0 반전 | **타일0** ✓ |
| `0x02` `0x03` | 타일1 / 반전 | 1px 왼쪽 / 1px 오른쪽 막대 ✗ |
| `0x04` `0x05` | 타일2 / 반전 | 타일0 ✗ |

`0x02`·`0x03` 이 **좌우 대칭**으로 나온 게 결정적입니다. 반전 비트는 살아 있고
인덱스 해석도 `바이트>>1` 이 맞는데 **인덱스 1 이상이 전부 쓰레기**입니다.

→ **텍스트 경로는 레코드에서 타일을 한 장(0번)만 로드합니다.**
말풍선 프레임(`0x95`)은 다른 코드 경로로 그리는 것으로 「추정」됩니다.

### 두 번째 벽 — 코드 자리

    서로 다른 음절 392종  vs  쓸 수 있는 코드 약 244칸 (0x00~0xF7, 예약 0x95~0x98 제외)

빈도 상위 244음절에 코드를 다 줘도 267페이지 중 **161페이지(60%)** 만 덮입니다.

### 디버거는 없습니다

mednafen **NGP 코어에 디버거가 없습니다.** 설정에 `md/nes/pce/pcfx/psx.debugger.*` 만 있고
`ngp.debugger.*` 가 없습니다. 토글 키를 수식키 없는 키로 재바인딩하고
`debugger.autostepmode 1` 까지 켜도 열리지 않습니다.
TLCS-900H 디스어셈블러도 apt·pip·npm 어디에도 없습니다.

## 8. 미해결 두 건

### J. `FAIR & SQUARE` (라운드 시작 콜, 영문)

실기에 라운드마다 나옵니다. 「いざ尋常に」의 의역입니다.
화면 픽셀을 원본 해상도로 복원해 **롬 전체 타일과 대조**했지만 일치 0건 → **압축 추정**.

참고: 제가 「勝負」(勝 7×7 `0x073CB7` + 負 5×7 `0x073EB1`)를 라운드 전 콜로 봤는데
근거가 약합니다. 승패 표시일 가능성이 큽니다. 현재 승/부로 들어가 있으니
일본어 모드에서 확인해 보시고 어색하면 `gfx2.ITEMS2` 에서 되돌리면 됩니다.

### K. 어트랙트 모드 캐릭터명

데모에서 `SHIZUMARU HISAME` 등이 영문으로 나옵니다.
`0x06B209` 등 우리가 고친 자리는 한글이 맞게 들어가 있는데 데모는 다른 자료를 씁니다.
`0x1B8A59` 부근에 같은 타일이 일부 있으나 **우리 맵 형식이 아닙니다.**

## 9. 검증 방법 — 다음에도 쓰세요

### 에뮬레이터 자동 검증

    Xvfb :99 → mednafen (DISPLAY=:99) → xdotool 키 입력 → import 로 캡처

키 매핑(mednafen 기본, SDL 스캔코드): A=`KP_2` B=`KP_3` OPTION=`Return`, 방향 `w a s d`.

**원본 해상도 복원이 핵심입니다.** 캡처한 루트 이미지에서 게임 화면은 480×456(3배 확대)이고,
3픽셀마다 하나만 뽑으면 **원본 160×152 가 그대로 복원**됩니다.
이게 있어야 롬 타일과 화면을 1:1 로 대조할 수 있습니다.

⚠ 창 위치가 실행마다 달라집니다. 원점을 고정하지 말고 **3×3 블록이 균일해지는 오프셋을
탐색**해서 찾으세요. (`(max-min).mean()` 이 0 이 되는 지점)

## 11. 다시 생각해 볼 지점

막힌 셋(H·I·J)이 **전부 압축 하나**로 수렴합니다. 우선순위는 명확합니다.

**1순위 — 압축 해독.** 풀리면 메뉴·옵션·HUD 이름·`SLASH`/`HIT`·`FAIR & SQUARE` 가 한꺼번에 열립니다.
   접근: 폰트가 VRAM 에 채워지는 순간의 소스 주소를 잡는 것. 디버거 있는 환경이 필요합니다.

**2순위 — 렌더러 어셈블리 (`0x00F82B`).** 받침 타이핑용. 고칠 지점은 둘 중 하나입니다.
   - 글자 하나 그릴 때 다음 스트림 바이트를 아랫줄 같은 칸에 그리고 커서는 1칸만 전진
     (데이터는 `t1 b1 t2 b2 …` 로 섞음) — 근본 해결, 코드 자리 문제도 사라짐
   - 타이핑 지연 제거 — 간단, 연출이 바뀜

**둘 다 TLCS-900H 디스어셈블러가 있는 환경이 전제입니다.**
없이 진행하면 바이트를 손으로 해독해야 하는데, 틀리면 조용히 깨집니다. 권하지 않습니다.

**당장 할 수 있는 것**: K(어트랙트 이름)는 압축이 아닐 수도 있습니다.
자료구조만 알아내면 데이터 패치로 될 가능성이 있어 비용 대비 가능성이 제일 높습니다.
