# ASCII 폰트 — 최종 결론 (2026-08-16)

앞서 두 번 말을 바꿨습니다. 이번엔 **실험으로 끝까지 확인했습니다.**

## 결론

**v0.5 README 가 맞습니다. 화면에 쓰이는 ASCII 폰트는 압축 저장돼 있습니다.**

`0x05291D` 뱅크는 평문이지만 **화면에 쓰이지 않는 별도 사본**입니다.

## 증거 넷

### 1. 화면 글리프와 `0x05291D` 뱅크가 픽셀 단위로 같다

메뉴 화면을 원본 해상도(160×152)로 복원해 8×8 셀을 떼어 뱅크와 대조했습니다.

    1  P  D  E  S  U   → 전부 픽셀 단위 완전 일치

그래서 처음에 "이 뱅크가 쓰인다"고 판단했습니다. **틀렸습니다.**
같은 건 *폰트 디자인*이지 *데이터 출처*가 아닙니다.

### 2. 뱅크를 고쳐도 화면이 안 바뀐다

`0x21`(`!`) `0x22`(`"`) `0x23`(`#`) 자리에 한글 「인 대 전」을 써 넣고,
문자열 `1P MODE` 를 그 코드열로 바꿔 실행했습니다.

    화면 결과 : 1 ! " #      ← 원래 문장부호 그대로
    기대했다면: 1 인 대 전

**문자열 치환은 먹혔는데(글자 수·위치가 바뀜) 글리프는 안 바뀝니다.**
뱅크는 화면의 출처가 아닙니다.

### 3. 코드 0x60 이상은 소문자로 나온다

`ss1_ui.py` 를 켜면 메뉴가 이렇게 나옵니다.

    1인 대전  →  1 g   h i        (코드 0x67='g', 0x68='h', 0x69='i')

우리 뱅크는 `0x60`~`0xFF` 가 전부 `FF`(빈칸)입니다. 빈칸이면 아무것도 안 나와야 합니다.
**소문자가 나온다는 건 실제 폰트가 소문자까지 갖춘 더 큰 폰트라는 뜻입니다.**
우리 뱅크(0x20~0x5F, 64글자)보다 범위가 넓습니다.

### 4. 그 소문자는 롬 어디에도 평문으로 없다

화면에서 뜬 소문자 `g` 와 `h` 의 8×8 비트맵을 그대로 떠서 롬 2MB 전체를 훑었습니다.

| 인코딩 | 결과 |
|---|---|
| 1bpp MSB 우선 | 0건 |
| 1bpp LSB 우선 | 0건 |
| 2bpp 리틀엔디언 (잉크=3) | 0건 |
| 2bpp 리틀엔디언 (잉크≠0) | 0건 |
| 2bpp 빅엔디언 (양쪽) | 0건 |

에뮬레이터 바이너리(`/usr/games/mednafen`)도 같이 훑었습니다 — **0건**.
BIOS 내장 폰트였다면 여기서 나왔어야 합니다.

→ **카트리지 안에 있는데 평문이 아니다 = 압축이다.**

## 다음 사람에게 — 이건 나쁜 소식이 아닙니다

세 가지가 확실해졌습니다.

1. **폰트는 카트리지 안에 있습니다.** BIOS 가 아닙니다. 즉 **패치 가능한 대상**입니다.
2. **글리프 디자인은 이미 손에 있습니다.** `0x05291D` 사본이 화면 폰트의
   `0x20`~`0x5F` 구간과 픽셀 단위로 같습니다. 압축만 풀면 넣을 그림은 준비돼 있는 셈입니다.
3. **빈 코드 자리가 넉넉합니다.** 실제 폰트는 최소 `0x20`~`0x7A`(소문자까지) 를 덮습니다.
   그 위쪽을 한글에 쓸 수 있는지가 관건인데, 문자열 치환 자체는 이미 동작이 확인됐습니다
   (코드를 바꾸면 화면 글자 수와 위치가 그대로 따라옵니다).

남은 건 **압축 포맷 하나**입니다. 그것만 풀리면 메뉴·옵션·전투 HUD 이름·`SLASH`/`HIT`·
`FAIR & SQUARE`·데모 캐릭터명이 **한꺼번에** 열립니다. 전부 같은 벽 뒤에 있습니다.

추천하는 접근은 압축 블롭을 정적으로 찾는 게 아니라, **에뮬레이터 디버거로
VRAM 폰트가 채워지는 순간의 소스 주소를 잡는 것**입니다. mednafen 은 `-debugger 1` 로
띄울 수 있고, 폰트 타일이 올라가는 VRAM 주소에 쓰기 브레이크포인트를 걸면
복사 루프의 소스 포인터가 바로 나옵니다. 그게 압축 블롭의 위치이자
압축 해제 루틴의 입구입니다.
